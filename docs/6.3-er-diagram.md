# 6.3 ER Diagram

## Overview

The OTech Fleet Management System uses a **MongoDB** database with six core entities and three lookup tables. The model supports the full vehicle trip request lifecycle: from employee submission through manager approval, fleet assignment, and trip completion.

---

## Entities

### User
Stores all system users (employees, managers, fleet coordinators, administrators).

| Attribute | Type | Description |
|-----------|------|-------------|
| _id (PK) | ObjectId | Unique user identifier |
| employeeId | String | Official HR employee ID (e.g. EMP-1042) |
| fullName | String | Display name |
| email | String | Login email (unique) |
| passwordHash | String | Hashed password |
| department | String | Department name (from Department lookup) |
| defaultBranch | ObjectId (FK) | Optional default branch |
| role | Enum | employee, manager, fleet_coordinator, admin |
| isActive | Boolean | Account active flag |

---

### Vehicle Request
Represents a trip request submitted by an employee.

| Attribute | Type | Description |
|-----------|------|-------------|
| _id (PK) | ObjectId | Internal ID |
| requestNumber | String | Human-readable ID (e.g. REQ-2024-001) |
| requester | ObjectId (FK) | Reference to User |
| branch | String | Departure branch |
| destination | String | Trip destination |
| purpose | String | Business reason for travel |
| travelDate | Date | Scheduled departure |
| returnDate | Date | Expected return (computed from trip duration) |
| tripDuration | Enum | 2h, 4h, 1d, 2d, 3d, 1w |
| numberOfPassengers | Number | Passenger count |
| priority | Enum | Normal, Urgent |
| status | Enum | Draft, Submitted, Approved, Rejected, Vehicle Assigned, Completed, Cancelled |
| rejectionReason | String | Reason if rejected |
| decidedBy | ObjectId (FK) | Manager/admin who approved/rejected |
| decidedAt | Date | Decision timestamp |
| submittedAt | Date | When employee submitted |
| cancelledAt | Date | When request was cancelled |

---

### Vehicle Assignment
Links an approved request to a specific vehicle and driver.

| Attribute | Type | Description |
|-----------|------|-------------|
| _id (PK) | ObjectId | Internal ID |
| assignmentId | String | Unique assignment code |
| request | ObjectId (FK) | Reference to Vehicle Request (unique — one per request) |
| vehicle | ObjectId (FK) | Reference to Vehicle |
| driver | ObjectId (FK) | Reference to Driver |
| assignmentDate | Date | When assignment was made |
| returnedAt | Date | When trip was completed / vehicle returned |
| notes | String | Coordinator notes |

---

### Vehicle
Fleet vehicle records.

| Attribute | Type | Description |
|-----------|------|-------------|
| _id (PK) | ObjectId | Internal ID |
| vehicleId | String | Fleet ID (e.g. VEH-001) |
| plateNumber | String | License plate (unique) |
| model | String | Vehicle model |
| vehicleType | String | Sedan, SUV, Van, etc. |
| seatingCapacity | Number | Max passengers |
| currentMileage | Number | Odometer reading |
| status | Enum | Available, Assigned, Under Maintenance, Inactive |

---

### Driver
Authorized drivers for fleet trips.

| Attribute | Type | Description |
|-----------|------|-------------|
| _id (PK) | ObjectId | Internal ID |
| driverId | String | Driver code (e.g. DRV-001) |
| driverName | String | Full name |
| employeeId | String | Optional link to HR ID |
| licenseNumber | String | Driving license number (unique) |
| licenseExpiry | Date | License expiration date |
| isActive | Boolean | Active driver flag |

---

### Notification
System alerts sent to users on request status changes.

| Attribute | Type | Description |
|-----------|------|-------------|
| _id (PK) | ObjectId | Internal ID |
| recipient | ObjectId (FK) | Reference to User |
| type | Enum | REQUEST_SUBMITTED, REQUEST_APPROVED, REQUEST_REJECTED, etc. |
| title | String | Notification title |
| message | String | Notification body |
| request | ObjectId (FK) | Optional link to Vehicle Request |
| requestNumber | String | Denormalized request number |
| readAt | Date | When user marked as read |
| createdAt | Date | When notification was created |

---

### Lookup Tables

| Entity | Purpose |
|--------|---------|
| **Branch** | Office locations (HQ, Bole, etc.) — used on trip requests |
| **Department** | Org departments (Sales, IT, etc.) — used when creating users |
| **Destination** | Common trip destinations — used on trip request form |

Each lookup has: `_id` (PK), `name`, `isActive`.

---

## Relationships

| From | To | Cardinality | Description |
|------|-----|-------------|-------------|
| User | Vehicle Request | 1 : N | One user submits many requests |
| User | Notification | 1 : N | One user receives many notifications |
| Vehicle Request | Vehicle Assignment | 1 : 0..1 | One request has at most one assignment |
| Vehicle | Vehicle Assignment | 1 : N | One vehicle appears in many assignments |
| Driver | Vehicle Assignment | 1 : N | One driver appears in many assignments |
| Vehicle Request | Notification | 1 : N | One request can trigger many notifications |
| User | Branch | N : 1 | User may have a default branch (optional) |

## How entities support the process flow

1. **Employee** (User) creates a **Vehicle Request** with status `Draft`.
2. On submit, status becomes `Submitted`; system creates **Notifications** for managers.
3. **Manager** (User) approves → status `Approved`.
4. **Fleet Coordinator** creates a **Vehicle Assignment** linking **Vehicle** and **Driver** → status `Vehicle Assigned`.
5. On trip completion, `returnedAt` is set, vehicle status returns to `Available`, request status becomes `Completed`.
